Khalifa Foods · System Requirements · v0.3 · Sept 2026

A POS, website & mobile system for Khalifa Foods, DHA Lahore.

Windows POS on the counter, a public ordering website, and a read-only mobile companion. Cash only in MVP, single till, offline-first on the counter, everything on free tiers. Built for Khalifa Foods first; schema shaped so the same system can serve other restaurants later.

Overview

Three clients, one database, one sync path:

Client 01 · Counter
Desktop POS (Windows)
Electron + Next.js. One terminal per branch in v1. Local SQLite mirror keeps the till working when the internet drops.
Client 02 · Floor
Mobile companion
.NET MAUI (Android + iOS). Read-only viewer: live orders, stock levels, today's numbers.
Client 03 · Customer
Website
Next.js on Vercel. Landing, menu with prices & deals, QR-menu deep links, pickup / delivery ordering.

Backing them: Supabase (Postgres + Auth + Storage), Vercel (web + APIs), Resend (email), and a small outbox worker for offline sync.

Redesigned · 80 mm thermal

Layout spec

  • Width: 80 mm (72 mm printable at 203 DPI = 576 px).
  • Header — Khalifa wordmark bitmap (owner supplies vector), Urdu wordmark line, tagline in one line, address + phone in a two-line block. All centered.
  • Meta row — Order channel (DINE-IN / TAKEAWAY / ONLINE) + table (if dine-in) left, bill number right. Cashier name + terminal + timestamp on second line.
  • Line items — three columns: ITEM (variable) · QTY (right-aligned 3 chars) · AMOUNT (right-aligned 5 chars). Modifiers indented one em under their parent line. Deal expansion optional (show as one line "Group Bandi" or exploded lines with a header — configurable per print).
  • Totals block — Subtotal, Discount (with reason if present), Tax (always printed even if 0), TOTAL in a larger font.
  • Tender block — Cash tendered, Change.
  • QR code — encodes https://khalifafoods.com/r/<bill_no>. Deep-links to digital receipt (also useful for reprint / dispute lookup).
  • Footer — Thank-you line in EN + UR. Small "Powered by …" watermark line, single 8 pt.
  • Reprint watermark — reprints show "*** COPY ***" band across the meta row.
  • Reason strip — voided lines show "VOID" band and reason.

Printer implementation

  • Library: node-thermal-printer (Electron main-process addon; supports USB, network, Bluetooth ESC/POS).
  • Urdu rendering: font pre-rasterised to bitmap (Noto Nastaliq Urdu) then sent as ESC/POS graphics command — reliable across drivers.
  • Owner's printer model still to confirm; drivers finalised once we have the exact model.

Order intake behaviour

  • Order lands in Postgres with channel=online, status=received.
  • Supabase Realtime pushes it to the counter's desktop app — kitchen ticket auto-prints.
  • Customer gets confirmation email (Section 10, T04) with order-status link.
  • Cashier updates status via POS ("Preparing" → "Ready" → "Out for delivery" → "Delivered"); each transition can optionally trigger a status email.
  • Rate-limited: max 5 orders/hour per phone number (Section 12).

Offline & sync

Single POS terminal + append-only orders → conflict resolution nearly vanishes.

SourceWrites whatWhere first
Desktop POSOrders, payments, stock movements, voids, shift opsLocal SQLite → outbox → cloud
WebsiteOnline orders (append-only)Cloud Postgres → Realtime → desktop
MobileNothing—
Superadmin (web)Menu, prices, users, configCloud Postgres → Realtime → desktop
  • Orders are append-only. No update-update conflict class.
  • Idempotency keys — client-generated ulid, UNIQUE server-side.
  • Reconciliation — desktop calls GET /sync/pull?since=lastPulledAt on boot + every N minutes, then drains its outbox.
  • Sync worker — ~200-line Node worker inside Electron main process. Status bar chip: "Synced 12 s ago" / "Offline · 3 in queue".
  • Mobile pulls deltas every 5 min while foregrounded. Never writes.

Bilingual — English & Urdu, day one

  • Storage: users.locale = en or ur. Menu items store name_en, name_ur, description_en, description_ur.
  • Website: next-intl, prefix routes /ur/..., dir="rtl" on the html tag for Urdu, logical CSS properties throughout.
  • Desktop: shares Next.js pages, toggle in status bar.
  • Mobile (MAUI): RESX resources, FlowDirection for RTL.
  • Fonts: Noto Nastaliq Urdu (Urdu), IBM Plex Sans (English).
  • Print: bilingual when both name fields exist.

Pakistan-specific requirements

  • Currency: PKR, symbol Rs or ₨, whole-rupee display, decimals kept internally.
  • Sales tax: default 0 %. Rule engine per-branch / per-payment-method / per-category / effective-date, ready to switch on when the owner needs it. Never hard-code rates.
  • Bilingual receipts — Urdu via bundled Nastaliq bitmap for reliable ESC/POS.
  • Auth is email OTP + PIN for counter staff.
  • Ramadan schedule — Sehri/Iftar windows as menu-availability toggles; Friday prayer break; Eid closures.
  • Halal & allergen tags per item.
  • Corporate invoice — optional CNIC / NTN field on customer.
  • Raast readiness for v2 payments alongside JazzCash / EasyPaisa.

Non-functional requirements

Performance

  • POS action < 100 ms.
  • Receipt print < 500 ms after tender.
  • Website LCP < 2.5 s on 3G Fast.

Availability

  • Desktop offline for 72 h continuous.
  • Website 99.9 % (Vercel SLA).
  • Weekly cron pings Supabase to defeat the free-tier 7-day pause.

Security

  • Supabase RLS deny-by-default.
  • Rate limit public endpoints via Next.js middleware + tiny Supabase counters table.
  • Audit log: voids, refunds, price changes, user creation, permission changes, stock adjustments.

Backup

  • Nightly pg_dump via Vercel cron → Supabase Storage bucket (30-day retention).
  • Desktop SQLite snapshot on each shift close.
  • "Export everything" button in Superadmin.

Accessibility

  • WCAG 2.1 AA on customer website.
  • Large-tap-target mode on the POS.

Risks & standing assumptions

Assumptions I'm running with (correct me if wrong)

  • Single POS terminal at DHA branch.
  • Delivery is offered across a defined area (owner sets radius / flat-fee later); pickup available at branch address.
  • Deal names remain as-is (including the political-party-named pizza deals — this is a deliberate marketing choice).
  • The party-named pizza deal English labels in the doc ("Muslim League N", "Tehreek-e-Insaf" …) are database-only; the customer-facing menu shows the original Urdu name plus a neutral English label if needed.
  • À la carte prices marked ? in Section 06 will be supplied by the owner before P1's menu seed goes live.

Risks worth pricing in

  • Two client stacks (TS+React desktop/web, C# MAUI) — acknowledged tradeoff, mobile stays read-only.
  • Supabase free-tier pauses after 7 idle days — keep-alive cron mitigates.
  • Thermal printer model unknown — need model number from Khalifa before P1 driver work.
  • Free-tier storage cap — 1 GB fits ~20 K photos; migrate to R2 if we hit it.
